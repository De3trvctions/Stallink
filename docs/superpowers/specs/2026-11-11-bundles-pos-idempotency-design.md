# 固定套餐、自动优惠与可靠收银设计

日期：2026-11-11。状态：设计基准；代码实现与验收进度见 [实现计划](../plans/2026-11-11-bundles-pos-idempotency.md)。

## 1. 已确认的需求

- 用户确认先做「固定套餐与自动凑套」，本期不做「任意选 N 款」。
- 新增商品弹窗可选择「单品」或「套餐」。套餐下面选择多个真实单品，并设置每种单品的数量；允许在同一流程中创建缺少的单品。
- 每个单品有自己的图片、价格、库存，可独立购买。套餐有自己的名称、图片和整套价。
- 同一单品多买优惠继续可配；分别选齐套餐组成商品后自动享受优惠。沿用此前确认的「优惠包组合最低价」。
- 店铺、活动、平台商品审核，以及电脑／平板／手机适配继续适用。
- 订单的创建、收款、交付、取消以及以后新增的退款操作必须幂等。
- 本轮交付调研与实现计划，不更改业务代码和运行数据。

图片中的「多张海报」应成为多个可销售单品；商品相册只描述同一单品，不承担套餐组成关系。以图片中的文字和张数作示意：4 张 Solo × RM20 + 2 张 CP × RM25，单买共 RM130，整套 RM120。真实款名、组成与价格由店主录入，不从示例图生成商店数据。

## 2. 实施前代码基线与原始缺口

| 当前实现 | 本轮需要补的能力 |
| --- | --- |
| `server/internal/data/schema.go`：`goods`、`event_listings`、`good_images` | 尚无跨商品的套餐组成、套餐活动价格与审核模型 |
| `server/internal/catalog/pricing.go`：`BundleTotal` | 只计算同一 SKU 的多件优惠，不理解不同商品凑套 |
| `server/internal/data/order_store.go`：`CreateOrder` | 无请求幂等键；事务可保证一次请求原子完成，但不能合并网络重试 |
| `PayOrder`、`CancelOrder`、`changeStatus` | 已锁订单行；重复操作一般返回状态冲突，未提供稳定结果重放 |
| `applyStock` | 支付时才扣库存；创建的待付订单没有库存预留 |
| `web/src/app/counter/page.tsx` | 点击加一和本地单品优惠预览已存在；无套餐、权威报价、持久化提交身份 |
| `web/src/app/counter/orders/page.tsx` | 操作缺少可靠的错误反馈和订单明细；重试未绑定原命令 |
| `schema.go` 启动时回填 `line_total_minor = 0` 的旧语句 | 新套餐分摊可能合法产生零分明细，不能被每次启动重算 |

## 3. 官方资料调研与采用方式

以下是功能模式参考；右栏为 Stallink 的设计建议，不代表第三方平台提供完全相同的自动最优价算法。

| 官方资料 | 已核实的模式 | 在 Stallink 中采用 |
| --- | --- | --- |
| [Square：创建与编辑套餐](https://squareup.com/help/us/en/article/8057-create-managing-bundles-with-square-for-retail) | 新建商品时选 Bundle，再选择组成商品、数量与套餐价格 | 一个新增入口，按类型展开不同表单 |
| [Shopify：套餐类型、库存与限制](https://help.shopify.com/en/manual/products/bundles/eligibility-and-considerations) | 区分固定套餐与同品多件包；套餐库存取组成库存除以需求数量后的最小整数 | 套餐引用单品，共用库存；首期禁止套餐嵌套 |
| [Square：自动应用优惠](https://developer.squareup.com/docs/catalog-api/cookbook/auto-apply-discounts) | 数量、商品组合、类别等可触发价格规则 | 自动识别凑套，并显示命中的优惠及省下金额 |
| [Shopify POS：商品搜索](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/inventory-management/searching-for-products) | 支持名称、SKU、条码等检索并加入购物车 | 第一阶段名称／套餐／活动筛选；第二阶段 SKU 与扫码 |
| [Shopify POS：快捷网格](https://help.shopify.com/en/manual/sell-in-person/getting-started/smart-grid) | 常用商品和操作可作为快捷入口 | 套餐卡片一键加整套，常售商品固定在前 |
| [Shopify POS：暂存购物车](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/order-management/manage-recent-carts) | 可保存、恢复购物车，跨设备已结账的购物车不可再次结账 | 先实现本机恢复和稳定 checkout ID，再增加服务器挂单 |
| [Stripe：幂等请求](https://docs.stripe.com/api/idempotent_requests)、[Square：幂等](https://developer.squareup.com/docs/build-basics/common-api-patterns/idempotency) | 相同键重试返回原结果；同键不同请求应报错 | PostgreSQL 保存命令身份、请求指纹和已提交结果；不照搬 Stripe 的全部错误缓存策略 |
| [PostgreSQL：INSERT](https://www.postgresql.org/docs/current/sql-insert.html)、[行锁与死锁](https://www.postgresql.org/docs/current/explicit-locking.html) | 唯一约束可协调并发插入；一致的锁顺序可降低死锁 | 幂等记录与订单／库存同一事务提交；所有写路径遵循同一锁顺序 |

## 4. 模型选择

| 方案 | 判断 |
| --- | --- |
| 在一个商品上放多张图，当作套餐 | 无法分别定价、库存和交付，不满足需求 |
| 给商品加 parent ID，子商品拥有一套复制库存 | 同品参加多套时库存会失真，历史订单也难追溯 |
| 独立套餐，引用现有单品及其需求数量 | **采用**；单品库存唯一，套餐可以重复引用同一单品，订单保存实际组成快照 |

### 4.1 商品、套餐与活动

- 保留 `goods` 作为单个 SKU。不同海报款式先分别建单品，不引入通用变体系统。
- 新增 `bundles`（所属店铺、名称、说明、审核信息）和 `bundle_components`（套餐、单品、每套数量、展示顺序）。一套至少 2 个不同单品、最多 20 个，每个需求数量 1–100；同一单品重复选择合并为一行。
- 新增 `bundle_images`，沿用现有 8 张相册、单张 6 MiB、JPG／PNG／WebP 的规则。
- 新增 `event_bundle_listings`：活动、套餐、单套价格、按「套数」配置的 `price_tiers`、是否上架。同一个套餐可参加多场活动，价格独立。首期所有合格的已上架套餐均参与自动凑套，不提供另一套「仅手动享价」模式。
- 套餐不设置独立实物库存，不对 `goods.total_stock` 再复制一份库存。组成单品必须属于同一店铺，并存在当前活动的上架记录。
- 单品可以被多个固定套餐引用。首期不支持套餐包含套餐、不支持跨店或跨活动凑套、不支持任意 N 款自选。
- 已被引用的单品使用归档／下架，禁止物理删除；旧订单读取交易快照。

### 4.2 管理端流程

1. 「添加商品」按钮打开现有弹窗，第一项为「单品／固定套餐」。
2. 选套餐：填写套餐资料和相册 → 搜索已有单品 → 设置每套数量 → 设置活动与套餐价 → 可选套餐多套优惠。
3. 套餐内每行展示封面、款名、单买价、库存和审核状态；可移除和排序。
4. 「新建单品」在弹窗内展开子表单。子表单保存在本次草稿中，最终提交时与套餐一起写入数据库；取消整个弹窗不会留下半成品单品。
5. 复用已有单品只建立引用，不复制商品。新增单品和套餐可一次送审；审核页能先审组成单品，再审套餐。
6. 多资源图片使用一次 multipart 提交：JSON 中以 `draftKey` 绑定新单品，文件字段使用 `bundleImages` 与 `componentImages.<draftKey>`。本次请求总大小不超过 50 MiB；每个资源仍最多 8 张图。客户端先提示总量限制，后端再次验证。
7. 图片先写暂存文件，再执行数据库事务；失败清理本次文件。崩溃遗留文件由扫描所有图片引用后的 24 小时清理任务回收。

### 4.3 审核与角色

- 建议权限：`shop_admin` 配置单品、套餐、价格与库存；`sales` 查看可售目录、报价和收银；`platform_admin` 按店铺审核单品与套餐；`customer` 查看公开目录。这会收紧当前 staff 可写商品的范围，实施时同步全部相关接口和菜单。
- 套餐本身和所有组成单品均已通过审核且本场上架，才允许新开单。任何一个组成单品不满足条件，显示明确原因。
- 改套餐名称、说明、图片、组成、单价或优惠后重新送审；只调整库存不触发审核。
- 组成单品的受审核内容变化时，同一事务将依赖套餐置为待审。平台审核必须核对当前组成版本，拒绝过期页面上的审核提交。
- 已预留订单保留成交价格；付款前仍检查店铺启用、商品审核／上架资格。若资格已撤销，订单取消并释放预留，返回可重放的业务结果。

## 5. 优惠规则与权威报价

### 5.1 一份购物车，一次最优计价

- 点击单品数量加 1；点击套餐加入每个组成单品所需的数量。库存始终按展开后的单品计算。
- 分别选齐所有组成商品也能自动凑套。相同实物数量从单品入口或套餐入口加入，最终金额一致。
- 同一件商品只能被一个优惠组合消耗一次；剩余数量继续参与单品多买优惠。套餐也可以设置「2 套多少钱」等数量包。
- 不按「先套餐再单品」贪心计价；比较全部合法组合，选最低总价。相同金额时按优惠应用条数较少、规则 ID 字典序确定结果，避免页面反复跳动。
- 金额全程使用整数分，API 金额同时受 int64 与 JavaScript 安全整数边界约束。

算法：先按存在套餐交集的商品拆成互不相交的组。预计算每个 SKU 的单品最优价 `S_i(n)`（`S_i(0)=0`），每种套餐单套价和多套优惠均变成「数量向量 + 总价」的 offer。只枚举套餐 offer 的使用，不逐个枚举单品排列。

```text
F(q) = min(
  sum(S_i(q_i)),
  offer.price + F(q - offer.componentQuantities)  // 每个数量足够的 offer
)
```

用剩余数量向量作 memo key，保留所用 offer 供收据展示。每次递归都减少实物数量。首期限制：一个连通组最多 20 个 SKU、10 个已启用自动套餐；购物车最多 100 个原始行、1000 件实物；每次报价最多探索 100000 个状态。保存规则时检测组规模；运行时超限返回 `422 pricing_complexity_exceeded` 并保留购物车，禁止静默改用非最优算法。性能验收不达标就阻止上线，不以错误价格兜底。

### 5.2 报价与订单

- 新增 `POST /api/staff/order-quotes`，输入活动、购物车及其版本，返回 `quoteId`、目录版本、有效期、展开后的单品、套餐分组、原价、优惠、总价、库存提示。
- 报价有效期 60 秒。报价不占库存；前端点击后先立即更新数量，再对 150ms 内的连续变化合并报价请求，忽略迟到的旧版本响应。
- 在报价未返回／过期／失败时，不允许使用本地旧金额提交。前端旧的 `bundleTotal` 仅保留展示用途，不再复制跨商品算法。
- 开单必须携带 `quoteId` 和期望总额。后端在事务内复核目录版本、报价归属、组成、金额与库存；不一致返回 `409 quote_stale`，展示新报价供重新确认，不静默涨价。
- 增加 `shops.catalog_revision`。所有影响价格、组成、审核资格的目录写事务先锁店铺行 `FOR UPDATE` 并递增版本；开单先 `FOR SHARE`，再读取并校验报价。报价在只读 Repeatable Read 事务中读取一致快照。
- 下单时保存组成、名称、数量、规则版本与实际成交金额快照；付款不按当前目录重新定价。
- 收款仍是现有的人工扫码到账确认；新增 `order_payments`，以订单 ID 唯一记录确认金额、币种、收款方式快照、操作者和时间。记录确认不代表系统发起了银行扣款。

### 5.3 成交分摊

- 新增 `order_pricing_groups` 保存每次命中的套餐／数量包及实收价。`order_lines` 只保存实际单品，不另加一份套餐库存行。
- 每个优惠组按组件原价权重分摊组价：先取整，再按小数余数从大到小补分，余数相同按单品 ID 排序。组内分摊总和必须等于组价。
- 单品既参加套餐又有散件时拆成独立成交行，关联对应分组；展示可聚合，账务和退货用原始分摊行。
- 所有成交行之和等于订单总额；允许合法的零分分摊行。新增 `snapshot_version`，用一次性迁移标记历史行，移除每次启动重算零金额的行为。

## 6. 订单幂等：必须先完成

### 6.1 请求契约

- 所有订单写命令要求 `Idempotency-Key`（UUID）；作用域为 `(shop_id, actor_id, operation, key)`。operation 包含动作和目标订单 ID。
- 首次 checkout 在发请求前生成并持久化 `clientOrderId`；订单表有永久唯一 `(shop_id, client_order_id)`。换请求键也不能让同一 checkout 创建第二单。
- 前端保存命令请求体、键及 checkout 身份。超时、断网、刷新后以同一键和同一内容恢复，不能在每次点击／重试时重新生成键。
- 请求规范化后计算 SHA-256：同类重复行合并、ID 排序、规范 UUID、拒绝非法数量及溢出；包含店铺、操作者、动作、目标、金额与报价等语义字段，不依赖 JSON 属性顺序。
- 同键同内容：返回原 HTTP 状态和 JSON，带 `Idempotent-Replayed: true`；同键不同内容：`409 idempotency_conflict`。
- 同一 checkout 换键但业务内容相同：找到原订单并返回原创建结果；业务内容不同：`409 checkout_conflict`。
- 创建命令的 `checkout_hash` 绑定原始 `quoteId`、`clientOrderId`、期望总额、称呼及操作者；换一份报价视为不同创建内容。已提交命令／checkout 的结果必须先查回，再校验新订单所需的报价期限和可售库存，不能因原报价后来过期而拒绝找回原单。
- 每次重放前重新验证登录、账号启用、角色及店铺归属。重放不绕过当前权限；跨店不能查询结果。

### 6.2 数据库事务

`order_commands` 保存作用域、请求指纹、目标订单、HTTP 状态、响应快照和提交时间。唯一约束竞争和业务动作在同一事务内完成：

```text
鉴权、结构校验、规范化
BEGIN
  INSERT command ... ON CONFLICT DO NOTHING RETURNING id
  若已存在：读取并比较指纹，返回已保存结果
  若本事务取得命令：
    锁定业务行 → 执行动作 → 写库存流水／审计 → 写响应快照
COMMIT
发送响应
```

- 并发同键请求由 PostgreSQL 唯一约束等待前一个事务；第一个回滚后第二个可以执行，第一个提交后第二个重放。
- 不同键并发使用同一 checkout 时，先以唯一 checkout 身份插入订单头，再预留库存；冲突事务读取原创建结果。第二个请求不得在识别原单前再次预留，或因为第一单已预留而误报库存不足。
- 不先提交「处理中」占位记录，不使用进程内 map 或 Redis 锁作为正确性依据。
- 锁等待最多 2 秒，整个写命令最多 5 秒；等待超时返回 `503 command_in_progress` 和 `Retry-After: 1`，客户端继续同键查询／重试。瞬时死锁或串行化错误最多重试事务 2 次，并检查 context；提交结果不明时必须按原键查询。
- 未提交事务失败全部回滚，包括幂等占位。只保存已提交结果：成功响应，以及会提交取消／过期等副作用的业务响应；参数错误和未执行动作的瞬时故障不固化。
- 响应记录保留到订单保留期结束；订单的 `client_order_id` 与业务指纹不按短 TTL 删除。以后若压缩响应正文，仍保留不可复用的身份记录。
- 原响应快照可能早于后续订单状态。前端重放后再 GET 当前订单，不能把已取消订单的界面退回已付款。

### 6.3 操作矩阵

| 命令 | 唯一业务效果 |
| --- | --- |
| 创建 | 一张订单、一次预留、一次创建审计；响应丢失仍找到同一订单 |
| 收款确认 | 一次预留转销售、一次收款记录；同单不同键重复确认同一收款信息也返回现有成功结果 |
| 交付 | 一次交付记录；已交付重试不重复审计 |
| 取消待付 | 一次释放预留；已取消重试返回现有结果 |
| 过期释放 | 与收款竞争同一订单锁，只有一个状态转换能够提交 |
| 记录退款（后续阶段） | 同一退款命令只记一次金额与回库流水；与取消分离 |

新键再次确认已付款订单但收款方式不同，返回 `409 payment_conflict`。订单已取消／过期后不能以新键付款。已付款／已交付订单不能走普通取消直接回库，返回 `409 refund_required`，由后续退款流程处理。

## 7. 库存预留与锁顺序

- 新订单成功创建时预留 15 分钟，返回 `reservationExpiresAt`，展示收款码前必须已经预留成功。
- `event_listings.reserved_qty` 记录本场待付占用；`inventory_reservations` 记录每张订单实际单品数量、到期时间与 active／consumed／released 状态。
- 本场可售数 = `listed_qty - sold_qty - reserved_qty`；套餐可售数 = `min(floor(组成单品可售数 / 每套需求数))`。
- 预留不改变 `goods.total_stock` 和 `sold_qty`；收款确认在一个事务中将预留转售，减少实物剩余并增加已售；取消／过期只释放预留。
- 配置库存时必须满足 `listed_qty >= sold_qty + reserved_qty`，并继续满足所有活动剩余分配不超过实物剩余库存的约束。
- 新增 `inventory_movements`，以 `(order_id, listing_id, movement_type)` 唯一约束记录 reserve／sell／release／restock，防止重复动作。旧订单不回填虚构的库存变动。
- 所有目录写操作：店铺独占锁 → goods 按 ID → listings 按 ID → 套餐及组成。所有订单命令：幂等键占位 → 店铺共享锁 → 目标订单锁 → goods 按 ID → listings 按 ID → 预留／流水。平台审核、旧商品修改、图片更新都要遵守店铺锁约定，避免只改新接口。
- 过期任务每 30 秒扫描到期 ID，逐单按相同顺序加锁并再次判断状态和数据库时间；支持多进程并发、重启补扫，不依赖前端倒计时。
- 付款事务使用数据库时间裁定是否过期；15 分钟到期后不收款。手工扫码场景若实际到账晚于过期，走店主异常处理，不重新扣款或伪造成功。
- 既有待付订单标为 `legacy_unreserved`；恢复旧单时先调用幂等的 reserve 命令，再显示收款码。失败保留原单并提示库存问题，不批量删除或自动扣库存。历史已付／已交付订单保持原账务与库存结果。

## 8. POS 与店面体验

- 收银页按活动选择目录；可切换「全部／单品／套餐」，搜索单品名、套餐名，显示商品图与可售数。
- 套餐卡展示组成缩略图、单买合计、套餐价和节省金额；点击整套加一，展开后也能独立调整单品数量。
- 购物车分别显示套餐分组、散件、优惠来源与最终应付。减少任一组成后立即撤销不再满足的套餐，不能残留优惠标签。
- 电脑：目录与购物车并列；平板：紧凑双栏；手机：单列商品、底部固定总价与购物车入口，抽屉内完成数量调整。关键触控按钮至少 44px。
- 网络中断显示「结果待确认」，保留提交身份并提供「恢复这次操作」。旧结果未确认前锁定该 checkout 的编辑和重新开单入口。
- 店面展示套餐卡与详情：完整组成、单买价、套装价、图片相册、可售数量、活动和摊位信息；价格来源和库存规则与收银一致。当前店面仍以浏览／现场购买为主，本期不新增顾客购物车报价接口或在线支付渠道。

## 9. 调研后建议的后续优化

| 优先级 | 内容 | 明确边界 |
| --- | --- | --- |
| 必需 | 套餐、精确最优价、幂等、预留、审核依赖、成交快照、订单详情 | 作为同一次核心能力升级交付 |
| P2 | SKU、USB 扫码枪输入、热门商品快捷入口 | 新增店铺内唯一 SKU；首期支持扫描器键盘输入，摄像头识码单独评估 |
| P2 | 服务器挂单／恢复、订单筛选、补打小票 | 草稿不预留库存，恢复后重新报价；checkout 后不能再结账同一草稿 |
| P2 | 全单退款／退货记录 | 店主确认实际退钱和是否收到实物；退款与回库独立记账、幂等；部分退款在有分摊快照后再扩展 |
| P3 | 在线支付及支付回调 | 选定支付服务后增加验签、唯一 provider event ID、支付金额／币种核对；网络回调不直接信任前端状态 |
| P3 | 任意 N 款、变体、会员、完整离线交易 | 不并入固定套餐首期；离线仅允许保存本地草稿，恢复网络后重新确认价格和库存 |

## 10. 核心验收样例

| 场景 | 预期 |
| --- | --- |
| A/B/C 各 RM20；ABC 套餐 RM55 | A+B = RM40；A+B+C = RM55；两套 = RM110 |
| A 单件 RM10、2 件 RM15 | A×3 = RM25；原规则继续成立 |
| A/B 各 RM10；A 两件 RM15；AB 套餐 RM16 | A×2+B = RM25，优于一套加一件的 RM26 |
| ABC RM55，BCD RM50；A/B/C/D 各 RM20 | 四件 RM70，选 BCD 套餐 + A；B/C 不可被两套重复消耗 |
| 套餐 A×2+B；A 可售5、B可售4 | 最多2套；与 A 单买共用同一份库存 |
| 同 checkout 连点／超时重发／刷新／服务重启 | 同一订单 ID；一次预留和审计 |
| 同键更换商品、数量、金额或收款方式 | 409，原订单和库存不变 |
| 并发付款、取消、到期释放 | 一个合法终态；库存和流水守恒 |
| 套餐改组成／改图／单品撤审 | 新单不可售，平台能看到准确依赖；旧成交明细不改写 |
| 合法零分组件后重启／重复迁移 | 仍为零，订单总额和分摊不变 |
